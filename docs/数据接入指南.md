# 真实数据接入指南

> 这份文档回答一个问题：**"没有真实积水数据"这件事，到底能不能解决、怎么解决。**
> 结论是：能，但要拿到政府侧的两类数据（积水监测、排水管网）。代码层面的接入点已经做好了。

---

## 1. 当前的数据状态（诚实版）

| 数据 | 现状 | 能否自主解决 |
| --- | --- | --- |
| 建筑/道路/行政区/湖面 | 真实（OSM、DataV） | 已解决 |
| 降雨预报、实况雨强 | 真实（Open-Meteo） | 已解决 |
| 汉口水位 | 推演值（曲线形状参考 2016 实测） | 部分：水文站数据可申请 |
| **各易涝点积水深度** | **模型推演值** | **需接入，见下文** |
| 避难所容量/联系人 | 台账重建（容量为估算） | 需民政/应急部门台账 |
| 排水管网 | 无 | 需市政/水务部门提供（真正的门槛） |

界面上「实时气象接入 / 2016·7·6 特大暴雨推演」两个模式，以及接口返回的
`metadata.data_source`（`model` / `observed`），就是为了不把推演值伪装成实测值。

## 2. 接入方式（三选一）

### 方式 A：外部系统直接推送（最简单，推荐先跑通）

任何能发 HTTP 的系统（水位计网关、视频分析服务、交警平台）都可以推：

```bash
curl -X POST http://localhost:8000/api/v1/ingest/readings \
  -H "Content-Type: application/json" \
  -d '{"readings": {"WL-江汉-032": 68.5, "WL-洪山-019": 12.0}, "source": "water-sensor-gw"}'
```

返回 `{"applied": 2}` 表示 2 个站点已生效。此时：
- `/api/v1/monitor/stations` 的 `metadata.data_source` 变成 `observed`
- 地图上这两个点的颜色、脉冲、告警条、灾情评估全部按实测值重算
- 未推送的站点仍用模型值（混合模式），不会因为数据缺失而中断

撤销覆盖：`DELETE /api/v1/ingest/readings`

### 方式 B：CSV 回放（历史复盘 / 无网现场演示）

```bash
# .env
INGEST_SOURCE=csv
INGEST_CSV=data/sample/readings_sample.csv
INGEST_SPEED=600        # 600 倍速：6 小时的数据 36 秒放完

python -m uvicorn backend.main:app --port 8000
```

CSV 格式（UTF-8，带表头）：

```csv
timestamp,station_code,depth_cm
2016-07-06 11:00:00,WL-江汉-032,68.5
2016-07-06 11:00:00,WL-洪山-019,12.0
```

`data/sample/readings_sample.csv` 是可直接跑的示例（20 个站点 × 13 个时刻）。
真实场次复盘时，把水务局提供的雨量/积水台账按这个格式导出即可。

### 方式 C：定时轮询外部接口（生产接法）

```bash
# .env
INGEST_SOURCE=http
INGEST_URL=https://your-gateway/api/v1/water-depth
INGEST_INTERVAL_SEC=60
INGEST_TOKEN=xxxx        # 可选，以 Bearer 方式发送
```

服务端兼容四种返回结构，取到任意一种即可：

```json
{"readings": [{"station_code": "WL-江汉-032", "depth_cm": 68.5}]}
{"data":     [{"code": "WL-江汉-032", "depth": 68.5}]}
[{"id": "WL-江汉-032", "water_depth_cm": 68.5}]
{"WL-江汉-032": 68.5}
```

### 运行状态查询

```bash
curl http://localhost:8000/api/v1/ingest/status
# {"enabled":true,"source":"csv","status":"running","pushed_stations":20,"last_error":null}
```

## 3. 数据从哪来（按可行性排序）

| 来源 | 做法 | 精度 | 成本 | 可行性 |
| --- | --- | --- | --- | --- |
| **视频 AI 积水识别** | 复用交警/城管现有摄像头，画面里放水尺或选参照物（路缘石、护栏），用分割模型算水深 | ±5cm | 中（每个点改造成本低，摄像头已有） | ★★★★ 最高 |
| **电子水尺 / 超声波水位计** | 在易涝点立杆装传感器，NB-IoT 回传 | ±2cm | 低（单点几百元） | ★★★★ 高 |
| **交警封路信息** | 接交管局封路事件流，作为"已阻断"的确定性输入 | 布尔 | 低（需协调） | ★★★ 中 |
| 12345 / 城管上报 | 人工上报文本，NLP 抽取地点+水深描述 | 粗 | 低 | ★★ 低（噪声大） |
| 水务局积水监测站 | 官方数据，最准 | ±2cm | 需授权 | ★ 取决于关系 |

**视频 AI 方案为什么最划算**：武汉主城区摄像头密度极高，不需要新增硬件，
只要在画面里找一个固定参照物做标定（例如路缘石高度 15cm、护栏立柱间距），
用单目几何就能反算水深，再按站点编码回传。这是目前行业内做城市内涝感知的主流做法。

## 4. 站点编码对齐（最容易踩的坑）

接入数据的 `station_code` 必须与 `data/processed/wuhan_waterlogging.geojson`
里的编码一致（形如 `WL-江汉-032`）。不一致的数据会被忽略，并计入
`/ingest/status` 的 `unknown_codes`，不会污染推演状态。

查看全部合法编码：

```bash
python -c "import json;d=json.load(open('data/processed/wuhan_waterlogging.geojson',encoding='utf-8'));print([f['properties']['station_code'] for f in d['features'] if f['properties']['station_type']=='waterlogging'][:10])"
```

如果外部系统的编码体系不同，在网关侧做一层映射表即可，**不需要改本平台代码**。

## 5. 从「模型」到「可用」还差什么

接入真实积水数据后：

- 沉浸深度、告警分级、地图着色 → 立刻变成实测驱动（已实现）
- 淹没区范围 → 仍是「深度 × 扩散系数」推算，**要精确得上水动力模型**

模型层的正确做法（行业内分工）：

```
排水管网 GIS + 地形 DEM
        ↓
SWMM / InfoWorks ICM（开源可用 SWMM）
        ↓  节点溢流量、地表积水深度栅格
本平台（可视化 + 调度 + 路径规划 + 指令下发）
```

**真正的门槛不是模型软件（SWMM 免费开源），而是排水管网 GIS 数据**——
管径、坡降、泵站、检查井，这些在市政/水务部门手里，不公开就拿不到。
没有管网数据，任何模型都只能做"趋势"而不是"定线"。

所以务实的路线是：

1. 先接 1~2 类感知数据（视频识别 / 水尺），把"推演"变"监测"——**本周就能做**
2. 拿管网数据，用 SWMM 做排水片区建模——**取决于数据授权**
3. 用历史场次（2016/2020/2024）率定参数，才能谈"预报精度"
